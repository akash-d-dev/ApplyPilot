01 / Big picture

Two separate phases

Preparation produces job-specific documents. The browser phase visits the application website, handles supported login steps, fills fields, uploads documents, and optionally submits.

Prepare

Find → understand → write

Job scrapers collect listings. Cursor scores them against your resume and preferences, then creates tailored resumes and cover letters for qualifying jobs. Playwright renders PDFs.

applypilot run or the existing start_applypilot.command launcher.

Act

Open → log in → fill → review or submit

A separate browser agent reads the prepared job, controls Chrome through Playwright MCP, and uses Gmail MCP if an email code is needed.

applypilot apply --agent cursor previews by default. Adding --submit enables real submissions.

Your target configuration: backend roles, remote from India, with full-time, part-time and contract roles allowed. The profile records six months of full-time experience separately from 2.5 years of internships. Unknown applicant facts must not be invented.

Resume reuse: when a resume already on the website belongs to the applicant and its displayed upload/update age is reliably under 24 hours, select it instead of uploading again. 03 / Architecture

Python coordinates; Cursor decides; MCP executes

Entry point

Terminal → ApplyPilot CLI → orchestration

cli.py loads configuration and chooses the command. pipeline.py runs preparation stages. apply/launcher.py selects and locks jobs, starts workers, records results and manages cleanup.

Text path

Scoring, tailoring and cover-letter modules call the shared chat() / ask() interface.

For Cursor, cursor_client.py launches the SDK bridge and creates a fresh tool-free agent for each request. Output is parsed and checked by the existing validators.

No browser tools in text stages
↔

Shared local state

SQLite stores job URLs, descriptions, scores, document paths, attempts and application results.

The profile, master resume, search configuration and generated files live under ~/.applypilot/.

Saved per completed job

Browser path

apply/agents.py starts a managed Python subprocess using the venv interpreter. cursor_runner.py runs a Cursor agent with MCP tools enabled and streams normalized events back to the dashboard.

Composer 2.5 explicitly receives fast=false in both text and browser paths.

→

MCP tool servers

Playwright MCP: Node process connected to that worker's Chrome debugging port. It navigates, inspects, fills, clicks and uploads files.

Gmail MCP: Node process using saved Google OAuth credentials. It exposes email search and read tools for login verification.

Website + Gmail API

Chrome interacts with the employer or job board. Gmail MCP calls Google's Gmail API. Cursor chooses tool calls; it does not receive the Google OAuth client file as part of the applicant prompt.

Worker isolation

Each worker has a Chrome profile, debugging port, working directory and upload folder. SQLite transactions claim jobs atomically so workers do not select the same job.

Deadlines & cleanup

Browser runs have a 300-second deadline. The managed runner supports cancellation and subprocess cleanup for timeout, skip and shutdown.

Progress without extra AI

Titles, source, location, scores and counters come from existing records. Progress logging makes no extra model requests. Preview counts and submitted counts remain separate.

04 / What we actually set up

Gmail MCP: one-time authorization, then reusable access

The failed Indeed login offered “Sign in with a code instead”. It sent an OTP, but Gmail MCP could not read it because credentials had not been configured. We used the app's existing Gmail MCP integration, not a new custom server.

  1. Created a Google Cloud project and enabled Gmail API

    This gives the OAuth client a project where the Gmail API is available. The consent setup uses an External audience with your Gmail account added as a test user.

  2. Created an OAuth client: Desktop app → ApplyPilot

    You checked “Use this client for an AI-powered agent”. That designates the client's intended use; actual Gmail access comes from the OAuth scopes requested during consent.

    You saved the downloaded client JSON at:

    /Users/akash/Desktop/projects/ApplyPilot/secrets/gmail-oauth.json

  3. Placed the client JSON where this MCP server expects it

    mkdir -p ~/.gmail-mcp
chmod 700 ~/.gmail-mcp
cp /Users/akash/Desktop/projects/ApplyPilot/secrets/gmail-oauth.json ~/.gmail-mcp/gcp-oauth.keys.json
chmod 600 ~/.gmail-mcp/gcp-oauth.keys.json

    The folder is accessible only to your user. The client JSON is readable and writable only by your user. The repository's secrets directory is ignored by Git.

  4. Ran the existing server's authentication command

    npx -y @gongrzhe/server-gmail-autoauth-mcp@1.1.11 auth

    The server opened Google's consent page. You authenticated with your Gmail account and authorized access. Google redirected the browser to http://localhost:3000/oauth2callback, where the local auth process exchanged the authorization code for tokens.

  5. Saved the resulting tokens and tightened permissions

    The server printed Authentication completed successfully and saved its credentials file.

    chmod 600 ~/.gmail-mcp/credentials.json

    gcp-oauth.keys.json identifies the OAuth application. credentials.json contains the access/refresh credentials produced after your consent. The latter allows later MCP runs to access Gmail without a new manual sign-in while authorization remains valid.

  6. Retried the application queue

    The first job had been marked login_issue and excluded from automatic submission retries. We reset that failed record so it could be selected first again. This reset did not remove scores, resumes or cover letters.

Login order: reuse the saved website session, then try Continue with LinkedIn using the existing applicant session, followed by Continue with Google using an already signed-in account matching the applicant email. If that cannot finish, use a fresh website email code/link through Gmail MCP, followed by a configured website password. Google password entry, 2FA, recovery and new OAuth consent remain manual. If login methods fail, explicitly enabled job-portal signup uses the profile email and locally configured portal password, then Gmail MCP completes email verification. Existing accounts are not duplicated, and rejected passwords are not silently replaced. LinkedIn basic identity/profile/email consent is allowed for the job portal, but posting, messaging and contacts permissions are forbidden. No LinkedIn or Google account is created. Portal registration may happen in preview mode; application submission still requires --submit.

At runtime

1. The browser requests an email code from the job website.
2. Cursor calls Gmail search_emails and read_email.
3. It reads the relevant verification message and enters the code in the job website.
4. The browser continues with the application.

This is the intended login path. The setup transcript proves authorization succeeded; it does not itself prove a later OTP was retrieved successfully.

Permissions: exact current behavior

The server requested gmail.modify and gmail.settings.basic. These are broader than the permissions needed just to read OTPs.

ApplyPilot's Cursor hook allows Gmail search/read. It denies email sending in preview mode and allows send_email in submission mode. Other Gmail writes are denied by the hook. This tool policy does not narrow the underlying Google OAuth grant.

How the app finds Gmail MCP

Each browser worker receives an inline MCP configuration built by apply/launcher.py:

{
  "gmail": {
    "command": "npx",
    "args": ["-y", "@gongrzhe/server-gmail-autoauth-mcp"]
  }
}

The server uses ~/.gmail-mcp/ by default, independent of the worker's working directory. The authentication command was pinned to version 1.1.11; the existing runtime configuration does not pin a version.

Your Cursor API key authorizes Cursor model calls. It does not authorize Gmail. The Gmail connector in this chat is also separate from the local Gmail MCP process.

05 / Launch commands

Choose preparation, preview or submission

Start in the project directory:

cd /Users/akash/Desktop/projects/ApplyPilot

Prepare documents

.venv/bin/applypilot run score tailor cover pdf --validation strict

Reuses saved scores and completed documents. Does not launch the application browser stage.

Preview one

.venv/bin/applypilot apply --agent cursor --model composer-2.5 --limit 1

Opens visible Chrome and fills one job without final submission.

Submit up to ten

.venv/bin/applypilot apply --agent cursor --model composer-2.5 --submit --limit 10

Processes up to ten selected jobs sequentially and submits each successful application. Failures also consume the processing limit. Omitting --limit still defaults to one job.

Check setup and saved state

.venv/bin/applypilot doctor
.venv/bin/applypilot status

Check local requirements and database counts. These commands are not an end-to-end proof of OTP login or employer submission.

Retrying a blocked job

To retry one prepared job, use its original listing URL:

.venv/bin/applypilot apply --agent cursor --model composer-2.5 --url 'PASTE_JOB_URL_HERE'

This command previews. Add --submit to enable submission. For a broader reset, apply --reset-failed resets failed records but does not launch a browser. Before resetting a submission failure, inspect its outcome so an uncertain submission is not repeated.

Ctrl+C once skips the current browser job; twice stops the run. Composer 2.5 stays in standard mode because the SDK selection explicitly sets fast=false.

Ready does not mean guaranteed.

“Ready to apply” means prepared and unsubmitted, with either a direct application URL or an original listing URL. The browser may still encounter an expired vacancy, unsupported SSO, CAPTCHA, account setup, unconfirmed applicant facts or a location restriction.
